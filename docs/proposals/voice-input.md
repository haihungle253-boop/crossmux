## 0. 这份文档取代了什么

[ai-companion.md §13](ai-companion.md) 把语音列为「延后」，给了四条理由。
**其中第 3 条推理的是另一个设计，现在必须收回。**

原话是：

> 「Voice interaction wants low latency, an open microphone and a live
> connection… Continuous capture plus a held connection removes the battery
> life that is the device's main advantage.」

这段话描述的是**一个常开麦克风、长连接的语音助手**（小智那种形态）。
本提案要做的不是那个：**按住说话、松手结束、一次性上传**。它在功率上更接近
一次翻页，而不是一次通话 —— 麦克风只在按住时开，连接只在上传时建立。

所以第 3 条不成立。另外三条仍然成立，但性质变了：

| 原因 | 现在的状态 |
|---|---|
| 1. CrossMux 没有音频输入路径 | ✅ 仍然成立。这是本提案的主要工作量 |
| 2. 语音固件是专用设备不是阅读器 | ⚠️ 部分成立。我们不移植语音固件，只移植录音那一段 |
| 3. 产品气质冲突 | ❌ **收回。** 推理的是常开麦克风，不是按住说话 |
| 4. 常开采集耗电 | ❌ 随第 3 条一起收回 |

§13 里搜集的硬件事实仍然有效，本文档第 2 节沿用并补充。

## 1. 要解决的问题

**不是「想要语音」，是「输入太难」。**

Emrys 的原话：

> 「主要解决用户在墨水屏上直接输入很困难的问题。」

这块设备只有四个物理键（Back / Left / Right / Function）加一个侧边电源键，
**没有触摸屏**。输入一个自由问题要靠虚拟键盘逐字选字，中文尤其慢。

现有的缓解手段是 `questions.txt` 的预设问题 —— 按一下就发出去。它有效，
但只能问事先写好的问题。**一旦你想问的是「这一段里那个比喻是什么意思」，
现有的路就断了。**

值得记下的一条旁证：同类商业产品（Metalio E-ink 4）的 AI 页面首屏，
也是四张预设问题卡片。**面对同一个约束，独立得出了同一个答案。** 这说明预设
问题不是权宜之计，是这块屏的正解；但它也说明，商业团队补上的那一块正是语音。

## 2. 已经确定的事实

本节每一条都有出处。**没有出处的推测不写进这一节。**

### 2.1 硬件：麦克风存在且被验证过

厂商仓库 `ESP32-S3-ePaper-3.97` 的
`ESP-IDF/02_Mic_test/components/codec_board/board_cfg.txt`：

```
Board: S3_ePaper_3_97
i2s: {bclk: 14, ws: 47, dout: 48, din: 21, mclk: 13}
in_out: {codec: ES8311, pa: 39, use_mclk: 1, pa_gain:6}
```

这些引脚与 [waveshare-epaper-397.md](../engineering/waveshare-epaper-397.md)
的硬件契约逐条吻合，**唯一的例外是 `din: 21`** —— I²S 输入线。

`ESP-IDF/02_Mic_test` 是一个能跑的录音示例：长按录 3 秒（16 kHz），短按回放。
厂商另外还提供了整机语音助手固件
`Firmware/xiaozhi/ESP32-S3_e-Paper-3.97_xiaozhi.bin`。

**结论：这块板子的麦克风不是推测，是厂商自己跑通并发布过的。**

### 2.2 固件现状：输入这条路是主动关闭的

```cpp
// freeink-sdk/libs/hardware/AudioManager/src/AudioManager.cpp:293
std.gpio_cfg.din = I2S_GPIO_UNUSED;
```

`lib/hal/` 下只有 `HalAudioOutput.{h,cpp}`，没有对应的 Input。
`AudioManager` 的状态机只有 `Idle / Playing / Stopping / RestartPending`，
**没有录音状态**。

另外两条影响工作量的事实：

- AudioManager 直接用 `driver/i2s_std.h`，**没有**用 `esp_codec_dev` 那套
  编解码器框架；ES8311 的寄存器是手写的（例如音量 `codecWrite(0x32, ...)`）。
  好处是轻，代价是 **ADC 那一串寄存器要自己配** —— 厂商示例通过
  `esp_codec_dev` 白拿的那部分，我们得自己写。
- AudioManager 是**所有板子共享**的。按交接信第 0 节第三条（「一个文件只有
  一个主人」），录音必须做成 **waveshare 专属的能力开关**，形如现有的
  `CROSSPOINT_CAP_SOUND_FEEDBACK`，不能让别的板子跟着变。

### 2.3 同族板子：Metalio E-ink 4

CrossMux 已经支持这块板子（`platformio.ini:666` 起，
[metalio-eink4.md](../engineering/metalio-eink4.md)，CI 每轮都编译
`metalio_eink4_nightly`）。它同样是 ESP32-S3 + 800×480 SSD1677 + 16 MB flash，
厂商固件带语音问答。

但 [metalio-eink4.md](../engineering/metalio-eink4.md) 第 7–8 行明确写着，
CrossMux 的移植 **「does not migrate the reference's ESP-IDF/LVGL application
or add its audio, cellular, haptic or IMU features」**。

**所以 CrossMux 内部没有任何现成的音频输入实现可抄。** 两块板子的麦克风在
CrossMux 下都是闲置的，处境相同。

### 2.4 实测数字

| 数字 | 值 | 出处 |
|---|---|---|
| 一轮对话耗时 | **13 秒**，已被视为缺陷 | 交接信 §7.2，真机 |
| 最紧张时空闲堆 | **86 KB** | 提交 `8d06430`，真机 |
| 固件 flash 占用 | **92.6%**（6,066,802 / 6,553,600 字节） | CI run 35321377742 |
| PSRAM | 8 MB，启动时探测 | waveshare-epaper-397.md |

> flash 那一行取自同批构建的 papermono（S3 同族）。Waveshare 自己那一行没能从
> CI 日志中取到，而它额外内嵌两个 16 kHz WAV，只会更满一点。**动工前应当用
> `scripts/firmware_size_history.py` 量准。**

## 3. 不变量

沿用 [ai-companion.md §3.1–3.5](ai-companion.md) 与交接信第 3 节的全部条款。
本提案新增四条：

**3.1 麦克风只在按住时开。**
不做唤醒词，不做常开采集，不做语音活动检测（VAD）。松手即停，停即关闭。
这不是省事，这是这块设备能装麦克风的前提 —— 一个可能在偷听的阅读器，不是
阅读器。

**3.2 录音不落 SD 卡，除非用户明确要求。**
录音进 PSRAM，上传后释放。阶段 1 的验收会写 WAV 到卡上，那是**调试产物**，
功能完成后必须移除。录音是最私密的一类数据，不该悄悄留下副本。

**3.3 语音只做输入。**
回复走现有的文字路径。语音回复（TTS）是另一种产品形态，需要单独决定，不得
搭车进入本提案。理由见 §4.1。

**3.4 语音是新增路径，不是替换路径。**
预设问题、虚拟键盘必须继续可用。麦克风坏了、太吵、或者只是不想说话时，
设备不能因此哑掉。

## 4. 三个产品决定

### 4.1 语音只做输入，不做输出

文字回复现在就能用，零成本。语音回复要加 TTS、要播放、要处理「读到一半翻页
怎么办」，而且**会把这台设备变成一个会说话的东西** —— 那是另一种产品。

更实际的一条：文字回复可以**跳读**。一段两百字的回答，眼睛三秒扫完；听完要
四十秒，而且不能倒回去。在一个为「读」而生的设备上，让 AI 开口说话是降级。

### 4.2 按住说话，不做唤醒词

**交互：按住 → 说 → 松手 → 等 → 读。**

- 没有「它在听吗」的焦虑：不按就是没在听，物理上如此。
- 没有误触发。
- 功耗形态是离散的，和翻页同级。
- 四个按键的设备上，「按住」是一个本来就存在的手势。

**但有一个真实的约束：没有空闲的按键。**
[waveshare-epaper-397.md](../engineering/waveshare-epaper-397.md) 的契约里：
Function 单击 = Confirm（等 300 ms 双击窗口后），窗口内第二击 = Back，
**长按 300 ms = 保持 Confirm**；侧边电源键接在 AXP2101 上，短按和长按都
已有含义。

候选方案（需要 Emrys 定夺，都有代价）：

| 方案 | 代价 |
|---|---|
| A. 只在对话界面里，Function 长按 = 录音 | 最省事；但不是「全局唤起」，得先进搭子 |
| B. 阅读时 Left+Right 同时按住 = 唤起「随便问问」并录音 | 和弦手势，需要验证不误触 |
| C. 在设置里让用户把某个手势改绑 | 最灵活，最费工 |

**倾向 A 先做**（范围最小、可验证），B 作为阶段 3 之后的增量。

### 4.3 「随便问问」是独立入口，搭子留在书里

Metalio 把 AI 做成了独立页面。CrossMux 的搭子长在阅读器里，必须先打开一本书。
两者都对，**因为它们回答的是不同的问题**：

- **搭子**：关于这本书。带摘录、带整本书记忆、**有结构性的剧透防护**。
- **随便问问**：关于任何事。不带书的上下文，所以也不需要那套防护。

**不要把搭子改造成通用助手。** 通用助手到处都有；一个知道你读到第几页、
记得你上周吵过哪个角色、而且结构上拿不到你没读的那几页的搭子，别处没有。
把后者换成前者是净损失。

**「随便问问」的实现成本很低**：同一个代理、同一个令牌、同一套流式解析和渲染，
去掉摘录与书库注入即可。它也是语音最自然的落点 —— 读书时你想聊这本书，
随便问问时你想聊任何事。

## 5. 架构

```
墨水屏                         树莓派 huginn                   外部
──────                         ──────────────                  ────
[按住] 录音 → PSRAM
   │
   └── POST 音频 ──────────→  /stt  (whisper.cpp)
                                 │
                              文字 │
                                 ↓
「随便问问」或「搭子」 ─────→  /v1/chat/completions ──→ 模型
   ↑                             (已有，不改)
   └──────── 文字回复 ───────────┘
```

**关键点：语音只是在现有链路前面加了一段。** `/stt` 之后的一切 —— 人设、
历史、书库记忆、剧透防护、流式解析、分页渲染 —— **全部复用，一行不改**。

设备仍然只认 SD 卡上 `/companion/config.txt` 里的一个 endpoint，
`/stt` 的地址由它推导（与乌鸦的 `/raven/` 同样的做法）。

## 6. 分阶段实施

**倒着做：风险最大的放最后，每一阶段都有独立可验收的产物。**

### 阶段 −1：十分钟的验证（不写代码）

用手机浏览器打开现有的聊天页面，用输入法的语音输入，聊三次。

**它回答的问题**：对着机器开口说话，对 Emrys 来说是自然的还是别扭的。

**为什么必须先做**：如果答案是「别扭」，阶段 1 那块最重的活就不必做，
直接转向「按一下标记这一页」（交接信 §7.3）。**成本十分钟，可能省下几天。**

### 阶段 0：树莓派侧的语音转文字（不碰固件）

在 huginn 上装 whisper.cpp，给 `companion-proxy` 加一个 `/stt`：收 WAV，
返回文字。用手机录的音频或现成文件测。

**验收**：`curl` 传一个中文 WAV 上去，返回正确的文字。

**它回答的问题**：**Pi 5 转 10 秒中文要几秒？** 这个数字我们都不知道，
而它决定整个方案成不成立。若是 30 秒，方案要重想。

**风险**：零。固件一行没动。

### 阶段 1：固件能录音（不联网、不涉及 AI）

- 新增 waveshare 专属能力开关（`CROSSPOINT_CAP_AUDIO_INPUT`）
- AudioManager 增加 RX 通道（`din = 21`）与 ES8311 ADC 寄存器配置
- 新增 `lib/hal/HalAudioInput.{h,cpp}`，与既有 `HalAudioOutput` 对称

**验收标准很硬**：按住录 3 秒，写成 WAV 到 SD 卡，拔卡插电脑，**能听见人声**。

不需要网络，不需要 AI。它只回答一个问题：**麦克风真的通了吗。**

> 完成后按 §3.2 移除写卡的调试路径。

### 阶段 2：打通

按住录音 → PSRAM → 上传 `/stt` → 文字 → 现有对话链路。

**前置条件（硬性）**：必须先修交接信 §7.3 记的那个阻塞问题。
`AiChatClient::cancel()` 已经写好，但 POST 阻塞了 activity 的 `loop()`，
**没有任何地方能注意到按键**。录音要能随时松手取消、要有「正在录」的反馈，
在一个卡死的循环里做不到。

**屏幕给不了录音反馈**（墨水屏刷新太慢，做不了电平条），但**这块板有喇叭，
而且音效系统已经在跑**：开始「嘀」一声，结束「嘀」一声。这是这块屏唯一自然
的答案，而且复用现有的 `SoundFeedback`。

### 阶段 3：「随便问问」独立入口

**可以独立于语音先做，也应该先做。**

主菜单新增一个应用（`AppsMenuActivity` 已有注册与显隐机制），四张预设卡片
加自由输入，走现有代理，不带书的上下文。

成本很小，而且它是语音最自然的落点 —— 阶段 2 完成后，这个页面按住说话。

## 7. 预算

### 7.1 内存

16 kHz 单声道 16 位 = **32 KB/秒**。

| 时长 | 占用 | 放哪 |
|---|---|---|
| 10 秒 | 320 KB | **PSRAM** |
| 30 秒 | 960 KB | **PSRAM** |

**绝不能放堆里** —— 真机最紧张时只剩 86 KB（§2.4）。8 MB PSRAM 绰绰有余，
这是整件事成立的前提。

建议上限 **30 秒**并在接近时用音效提示，避免一次上传过大。

### 7.2 延迟

**必须诚实记下：语音会让等待变长，不会变短。**

| 环节 | 估计 |
|---|---|
| 录音 | 用户决定 |
| 上传 ~320 KB | 数秒 |
| `/stt` | **阶段 0 要测出来的数字** |
| 模型回复 | 13 秒（实测） |

总和大概率**超过 20 秒**。换来的是「不用戳键盘」，不是「更快」。

这也让阶段 2 的阻塞修复从「最好有」变成「必须有」：20 秒的卡死界面不可接受。

### 7.3 Flash（顺带回答「删掉游戏能腾多少」）

九个游戏（象棋、木鱼、五子棋、推箱子、数独、扫雷、像素开关、计算器、2048）
合计 **14,055 行**，其中内嵌资源约 42 KB（木鱼 28,152 字节 + 推箱子 14,603 字节），
其余为纯代码。**估算共约 100–160 KB，占固件 2% 左右。**

本提案**不依赖**删除它们：语音的代码量远小于这个数字，瓶颈也不在 flash。

顺带：`src/activities/settings/AppVisibilitySettingsActivity.cpp` 已经提供了
**在设置里隐藏应用**的功能。想让菜单清爽，**今天就能做到，不用改一行代码，
也不用承担分叉上游的代价。**

## 8. 风险与未解问题

1. **ES8311 的 ADC 寄存器序列**是主要未知。厂商示例通过 `esp_codec_dev`
   白拿，我们要手写。这部分**只能在真机上调**，云端无法验证。
2. **whisper.cpp 在 Pi 5 上的中文速度与准确度**未知。阶段 0 专门为此存在。
3. **录音质量**未知：板载麦克风、有外壳、有手持噪声。厂商示例能录到声音
   ≠ 语音识别能用。阶段 1 的验收标准（「能听见人声」）是为此设的。
4. **按键怎么分配**（§4.2）需要 Emrys 定夺，三个方案都有代价。
5. **树莓派曾有无法解释的文件损坏**（交接信 §8），**内存测试仍未做**。
   在那台机器上新增服务之前，值得先跑一次 memtest。

## 10. 明确不做的

- **不做唤醒词、不做常开麦克风、不做 VAD**（§3.1）
- **不做语音回复**（§4.1），另行决定
- **不把搭子改造成通用助手**（§4.3）
- **不为了省 flash 而删除游戏**（§7.3），隐藏即可
- **不自己分叉一份「简化版固件」**：阅读器是最不能坏也最难懂的部分，
  上游仍在持续修它。为省 2% 的空间接手 59 万行代码的维护责任，不划算。
